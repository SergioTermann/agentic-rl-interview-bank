# 第六课　做一个能被追问的工具调用 RL 项目

**研究问题。** 一名必须先查两家报价再提交的智能体，只有 16 条专家演示。再给同样的模型在线采样预算，奖励“完成核验”和奖励“完成提交”分别能带来什么？研究对象是工具选择与终局验证。已知规则在这个环境里能满分，因此它也提供了审计环境和奖励逻辑的办法。

## 面试交付标准

用 15 分钟向同伴演示下面五件事。让对方随机选一道题核对。

1. **任务定义。** 观察、动作、终止、预算和真实成功事件各是什么。
2. **一次更新。** rollout 保存了什么，old/ref/current logp 分别来自哪里，哪些 token 或动作进入 loss。
3. **可复现实验。** 命令、seed、版本、数据划分、方法差异和资源成本都能重跑。
4. **失败证据。** 至少一条模型看全信息仍选错的 trace，一条代理奖励高但真实核验失败的 trace。
5. **结论适用范围。** 说清训练和评估使用的任务分布，以及下一个可能推翻你解释的实验。

## 复现与读代码

脚本仅依赖 Python、PyTorch 和标准库，使用 CPU。工作区实测 Python 3.12.7、PyTorch 2.10.0+cu128。换电脑时先运行 `python -c "import torch; print(torch.__version__)"`；若缺 PyTorch，可在虚拟环境中用 `python -m pip install torch --index-url https://download.pytorch.org/whl/cpu` 安装 CPU 版。

```powershell
python lab/drills.py
python lab/train.py --methods rule random sft sft-grpo --seeds 3 --steps 8
python lab/train.py --seeds 3 7 19 --output runs/reproduction --cases
python lab/review.py runs/reproduction/cases.csv --split shift --seed 3
```

第一条检查张量、选中 token 概率和梯度；第二条是快速冒烟；第三条才是正式默认预算；最后一条对同一批任务做配对比较并打印失败样本。输出目录每次用新名字。已有的默认运行保存在[指标表](../lab/reference_run/scores.csv)、[逐步训练日志](../lab/reference_run/learning.csv)和[运行配置](../lab/reference_run/config.json)。

**带着四个问题读代码。** ① `make_tasks` 怎样防止两家报价对调后跨集合泄漏？② `observe` 怎样遮住未查数据？③ `rollout` 中提前提交后，余下步为何还存在于张量却不参与 loss？④ `rl_fit` 中哪一行改变代理奖励，哪一行保证旧 logp 不动？前三题答完，自己手写这段伪代码：采样同题 G 条 → 按题归一化 → 冻结行为概率 → 重放有效动作两次 → 独立验证。[训练与环境实现](../lab/train.py)

### 你必须能指到的代码位置

| 面试追问 | 你要打开的对象 | 现场应说出的细节 |
|---|---|---|
| 任务是否泄漏 | `make_tasks` | 交换供应商后的等价题使用同一 split，shift 只改变运费范围 |
| 未观察信息是否被偷看 | `observe` | `quotes * seen` 后才拼输入，判分器可以看隐藏真值，policy 不可以 |
| 哪里区分工具返回与策略输出 | `observe`；token 实验中的 `collect` | 报价版把工具结果作为七维状态的一部分。Transformer 版只对采样的两个动作 token 写入行为 logp，追加的工具观测供下一步读取 |
| old policy 是谁 | `rollout` 返回的 `old_logp` | 采样当时的 action logp，重放前冻结，更新两遍仍用同一分母 |
| ref policy 是谁 | `rl_fit` 的 `reference` | RL 开始时复制的策略，只用于参考 KL，不等同于本批行为策略 |
| 代理奖励改了哪里 | `rl_fit` 的 `submitted` 分支 | 提交即可得分，真实 `verified` 单独记录。二者的差值可以用失败轨迹核对 |
| 结果为什么可信 | `scores.csv`、`learning.csv`、`cases.csv` | 训练 reward 和贪心评估指标不是同一分布，逐题 trace 能回到原始报价 |

## 数据、对照和共同预算

训练池 1,024 题；dev、test、shift 各 256 题。商品价为 5–30 的整数，train/dev/test 中运费为 0–5，shift 中为 0–20。排除并列总价，题目及其供应商交换版本经过同一内容哈希切分。模型看七个数：两家已见商品价与运费、两位已查标记、剩余步数比例。完整报价只给环境判分。规则策略与 SFT 教师都先查 A、查 B，再用已见报价比较。

| 方法 | 存在的训练信号 | 实验角色 |
|---|---|---|
| `rule` | 可执行规则，无学习 | 校验任务确实可解，作为上界 |
| `random` | 等概率抽四个动作 | 单次随机策略基线 |
| `sft` | 16 条规则示范，交叉熵训练 80 步 | 只给少量专家演示能走多远 |
| `grpo` | 随机初始化，终局真核验 | 稀疏奖励下从头探索 |
| `sft-grpo` | 与同种子 SFT 相同的初始化，再用真核验 | 在线增量收益 |
| `sft-proxy` | 同样的 SFT 初始化，只要提交就得 1 | 单独替换奖励定义 |

三条 RL 分支各采 $60\times32\times8=15,360$ 条轨迹，每批重放更新两次。组内采用总体标准差；每条轨迹对动作求和再按轨迹平均。参考 KL 按当前访问状态枚举四动作计算，参考模型冻结为各分支 RL 开始时的模型，$\beta=0.01$。训练时随机采样；学习策略在测试时单次贪心，随机基线保留单次均匀采样。SFT 与 RL 的计算量不同，因此“增加在线训练”这项比较不能把收益全部归因于某个优化器。更强的对照可加入同采样预算的拒绝采样微调。

## 一份已跑出的结果

以下是三个训练种子 3、7、19 的平均核验成功率，单位为 %。各方法使用同一批评估任务。

| 方法 | dev | test | 运费偏移 shift |
|---|---:|---:|---:|
| 规则 | 100.00 | 100.00 | 100.00 |
| 随机 | 3.26 | 3.39 | 3.12 |
| SFT | 92.32 | 89.97 | 77.73 |
| 随机初始化 GRPO | 97.27 | 95.18 | 87.76 |
| SFT → 真核验 GRPO | 98.83 | 97.40 | 86.06 |
| SFT → 提交代理 GRPO | 91.93 | 90.23 | 76.82 |

**先解释最容易答错的一行。** SFT 加真核验 RL，在同分布 test 上平均从 89.97% 到 97.40%。但在更高运费的 shift 上，SFT 加 RL 三颗种子分别约 96.5%、90.6%、71.1%。随机初始化 GRPO 在这一列的三种子均值更高。这批数据支持在指定任务上的改善，也暴露了分布和种子依赖。要进一步讲“冷启动更好”，还需更多种子、预注册任务和同预算对照。

**再读代理奖励。** 种子 3 的 `sft-proxy` 在第 1 个 batch 的训练提交奖励已是 1.000，真实核验只有 0.875，零方差组占 100%。第 60 个 batch 的提交奖励仍为 1.000，真实核验约 0.883。这个代理目标给“判断哪家便宜”几乎没有区分信号。这里观察到的是奖励饱和，不能据此声称模型已经学会恶意利用奖励。`learning.csv` 中的奖励来自更新前的随机 rollout，`scores.csv` 来自评估时的解码；两者口径不同。

**一个可以复核的失败。** 对种子 3 的 `sft-grpo`，shift 任务 21 的 A 为商品 9、运费 14，B 为商品 13、运费 8。动作 `0 1 2` 表示查 A、查 B、交 A。两次查询齐全，A=23、B=21，错误发生在最后的决策。可能解释是模型在训练分布中过度依赖商品价。下一步可对已见报价做对称交换、控制总价差并改变运费占比，检验错误是否仍跟着商品价走。单个反例能定位失误的阶段，不能唯一确定网络学到了什么。

**这类失败有多普遍？** 从 `cases.csv` 取同一模型、同一种子、同一 shift 的全部 256 题。按 `(price_a − price_b) × (总价A − 总价B)` 的符号分组。正数表示商品价和总价指向同一赢家，负数表示排序相反。这里已排除总价相等，零表示商品价相同。参考运行中，排序一致的 196 题错 0 题，排序相反的 49 题错 9 题，商品价相同的 11 题错 0 题。请自己写一个分组统计，换到 seed 19，再比较各组总价差。错误集中在某个切片支持继续调查；总价差、位置偏好仍是可能的解释。

**配对展示。** 对上述同一颗种子、256 道 shift 题，真核验微调相对 SFT 多赢 18 题、多输 1 题，配对差为 $17/256=6.64$ 个百分点。按题重采样 2,000 次，固定脚本的 95% 百分位区间约为 [3.52, 10.16] 个百分点。这一行描述固定的两个模型；上表的 86.06% 是跨种子均值。区间口径与均值口径不要混用。[配对重采样与失败样本打印](../lab/review.py)

## 练习一次固定预算的消融

**建议从组大小开始。** 假设“每题减半采样，改为每批覆盖两倍任务，可在相同轨迹预算下取得相近或更高 dev 成功率”。在看数据前，把成功率差、非零方差组比例、调用总数、种子和判断规则写好。保持训练 60 批、每批 256 条轨迹、每批两次更新：

```powershell
python lab/train.py --methods grpo --group 8 --batch 32 --seeds 3 7 19 --output runs/g8
python lab/train.py --methods grpo --group 4 --batch 64 --seeds 3 7 19 --output runs/g4
```

从每份 `learning.csv` 算每批非零方差组占比 `1-zero_group`。训练调用量按 seed 将 `tool_calls` 对 60 批求和；`scores.csv` 中的 `queries` 另指评估时每题平均调用数。两个设置每个种子都采 15,360 条轨迹，改变的是这些轨迹如何分给题目。脚本同时打印固定评估集，开发决策看 dev。

| 种子 | G=8，dev 成功/256 | G=4，dev 成功/256 | G=8，训练工具调用 | G=4，训练工具调用 |
|---|---:|---:|---:|---:|
| 3 | 254 | 250 | 28,037 | 27,675 |
| 7 | 242 | 243 | 28,579 | 28,583 |
| 19 | 251 | 220 | 27,778 | 27,768 |

**怎样读这个结果？** 以 seed 19 为例，G=8 有 1,530/1,920 组得到不同奖励，G=4 有 2,322/3,840 组得到不同奖励。后者的有效组总数更多，占比却更低，dev 也少过了 31 题。seed 7 的方向相反。这三颗种子不足以说明某个 G 对所有任务都更好。在这个固定轨迹预算下，只看有效组总数挑配置，会在 seed 19 上选错。[按设置与种子保存的实测结果](../lab/reference_run/group_budget.csv)
